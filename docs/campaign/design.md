# Устройство: ECS и детерминизм

## Что где лежит

| Что | Где | Почему |
|---|---|---|
| Поселения | сущности ECS: `Settlement`, `Owner`, `RecruitQueue` | их много (на большой карте — сотни), их обходят каждый ход |
| Армии | сущности ECS: `Army`, `Owner`, `Location`, `Moves` | появляются и исчезают, их обходят каждый ход |
| Регионы | `CampaignMap` — обычный массив | не меняются за игру |
| Фракции | `Vec<FactionState>` | маленькая таблица, нужна по номеру |
| Типы юнитов | `Vec<UnitType>` | выжимка из `export_descr_unit.txt` |

Объекты ссылаются друг на друга короткими номерами (`FactionId`,
`RegionId`, `UnitTypeId`), а не строками.

## Детерминизм

Правила из [ADR о детерминизме](../adr/determinism.md) соблюдены так:

- **Мир меняется только командами** (`apply`) и концом хода (`end_turn`).
  Чтение (`settlements()`, `armies()`…) ничего не меняет.
- **Нет float** — все формулы целочисленные.
- **Нет обхода `HashMap`** — только запросы ECS (их порядок задан
  последовательностью операций) и массивы.
- **Случайность** только из `rm_core::sim`, поток `CAMPAIGN_EVENTS`,
  ключ — номер боя и сущности сторон.
- **Контрольная точка** — `Campaign::state_hash()`: хеш хода, очереди,
  фракций и всех компонентов ECS.

Тест `replay_from_commands_gives_the_same_hashes` проверяет это на деле:
30 ходов на автопилоте записываются как список команд, затем кампания
запускается заново, получает те же команды, и хеш после каждого хода
каждой фракции должен совпасть.

## Почему соседство регионов в тексте

В Medieval II соседство и положение поселений вычислялись из картинки
`map_regions.tga` (каждый регион — свой цвет пикселей). Разбора картинок
пока нет, поэтому соседство и координаты поселений лежат в новом
текстовом файле `descr_rm_regions.txt`. Когда появится разбор карты
регионов, его результат можно будет сверять с этим файлом или вовсе
заменить его.
