# Как работает разбор файла, шаг за шагом

Разберём на примере кусочка `export_descr_unit.txt`:

```
; мой юнит
type             Village Levy
dictionary       Village_Levy        ; Деревенское ополчение
soldier          levy_peasant, 60, 0, 1
banner faction   main_infantry
```

## Шаг 1. Лексер: текст → строки «ключ значение» (`lexer.rs`)

Функция `tokenize` идёт по файлу построчно и для каждой строки:

1. отрезает всё после `;` — это комментарий;
2. убирает пробелы и табуляции по краям;
3. пропускает строку, если она стала пустой;
4. первое слово считает **ключом**, остаток — **значением**.

Из примера получится:

| Строка | Ключ | Значение |
|---|---|---|
| 2 | `type` | `Village Levy` |
| 3 | `dictionary` | `Village_Levy` |
| 4 | `soldier` | `levy_peasant, 60, 0, 1` |
| 5 | `banner faction` | `main_infantry` |

Особый случай: у ключей `banner` и `era` в оригинальном формате ключ из двух
слов (`banner faction`, `banner holy`, `era 0`), поэтому второе слово
приклеивается к ключу.

Номер строки сохраняется: именно он потом попадёт в сообщение об ошибке.
Ещё лексер убирает невидимый символ BOM в начале файла, который иногда
добавляет «Блокнот» Windows.

## Шаг 2. Группировка в записи (`record.rs`, функция `group`)

Файл — это последовательность записей. Запись начинается с «открывающего»
ключа (`type` у юнитов, `faction` у фракций) и продолжается до следующего
такого же ключа. Пустые строки между записями ничего не значат, они только
для красоты.

Если до первой записи стоит какая-то строка, это ошибка: непонятно, к чему
она относится.

## Шаг 3. Разбор полей записи (`unit.rs`, `faction.rs`)

У записи (`Record`) есть три способа достать поле:

- `require("ключ")` — обязательное поле; если его нет, ошибка указывает на
  первую строку записи;
- `take("ключ")` — необязательное поле; если оно встречается дважды, ошибка
  указывает на повтор;
- `take_all("ключ")` — поле, которое может повторяться (например, `officer`).

Значения через запятую разбирает `Values`: проверяет, что значений хватает,
и превращает нужные позиции в числа. Если число не число, ошибка называет
поле, его смысл и то, что было написано:

```
u.txt:4: в `soldier`: число солдат должно быть числом, а написано `sixty`
```

Каждое поле разбирается независимо от остальных, поэтому в одной записи
можно сразу найти несколько ошибок. Готовый `Unit` собирается, только если
все обязательные части разобрались успешно.

Всё, что не было забрано, попадает в `extra` («неизвестные поля»).

## Шаг 4. Проверки между записями и файлами

- Два юнита (или две фракции) с одним именем — ошибка, с номером строки
  первого объявления.
- `GameData::check_references` проверяет, что все фракции из `ownership`
  юнитов объявлены в `descr_sm_factions.txt`. Имя `slave` (мятежники)
  разрешено всегда, как в оригинале.

## Шаг 5. Результат

Все функции возвращают либо готовые данные, либо `DataErrors` — список
**всех** найденных ошибок. Каждая ошибка печатается как
`файл:строка: причина`. Строка `0` значит «ошибка про файл целиком»
(например, файл не найден), и тогда номер строки не печатается.

## Как добавить новое поле

1. Добавьте поле в структуру (`Unit` в `unit.rs` или `Faction` в `faction.rs`)
   с комментарием, что оно значит.
2. В `parse_unit`/`parse_faction` достаньте его через `take` или `require`
   и разберите значение.
3. Добавьте тест в `crates/rm_data/tests/parsing.rs`.
4. Опишите поле в руководстве моддера в `docs/modding/`.
