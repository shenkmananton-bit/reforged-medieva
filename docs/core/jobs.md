# Система задач (job system)

Код: `crates/rm_core/src/jobs.rs`.

## Зачем

У процессора 4–16 ядер. Если система морали считает 10 000 солдат в одном потоке, остальные ядра простаивают. Система задач раздаёт работу всем ядрам.

## Как пользоваться

```rust
use rm_core::JobSystem;

let jobs = JobSystem::new();          // один раз при запуске игры

// Выполнить f(0), f(1), ..., f(n-1) на всех ядрах и дождаться
jobs.parallel_for(n, |i| { /* работа с элементом i */ });

// То же, но кусками: f получает диапазон индексов
jobs.parallel_for_batched(n, 256, |range| { for i in range { /* ... */ } });

// Две независимые задачи одновременно
let (paths, visibility) = jobs.join(|| compute_paths(), || compute_visibility());
```

В ECS обычно всё это не нужно вызывать руками: `world.par_for_each_mut(&jobs, ...)` сам режет сущности на куски (см. [ecs.md](ecs.md)).

## Как устроено

```
 главный поток           рабочие потоки (ядер − 1)
 ─────────────           ─────────────────────────
 parallel_for(n, f)
   ├─ кладёт задачу ───► просыпаются
   ├─ сам берёт индексы  берут индексы: next.fetch_add(1)
   │  next.fetch_add(1)  выполняют f(i)
   └─ ждёт, пока все n   последний закончивший будит главный
      будут готовы
```

- **Потоки создаются один раз** при `JobSystem::new()` и спят, пока нет работы. Создавать потоки каждый кадр было бы слишком дорого.
- **Главный поток тоже работает**, поэтому на 8 ядрах создаётся 7 рабочих потоков.
- **Раздача индексов — атомарный счётчик.** Кто освободился, тот и берёт следующий индекс. Так нагрузка выравнивается сама: если один кусок оказался тяжёлым, остальные потоки разберут остальное.
- **Паника внутри задачи** ловится, остальные индексы дорабатывают, а паника пробрасывается в поток, вызвавший `parallel_for`. Пул после этого остаётся рабочим.
- **Вложенный вызов** (`parallel_for` внутри `parallel_for`) или вызов одновременно из двух потоков не приводит к взаимной блокировке: такой вызов выполняется последовательно в своём потоке.

`JobSystem::with_threads(1)` выполняет всё в одном потоке. Это удобно для отладки и для проверки детерминизма.

## Правила для детерминизма

Порядок, в котором выполнятся `f(0)…f(n-1)`, **не определён** и меняется от запуска к запуску. Поэтому:

- каждая задача пишет только в «свою» ячейку (свою сущность, свой элемент массива);
- общие суммы и списки собираются **после** `parallel_for`, в фиксированном порядке;
- случайность — только через `Rng::for_entity(seed, поток, шаг, сущность)`.

Тест `same_commands_same_hash` в `world.rs` проверяет это: один и тот же сценарий на 1, 4 и 8 потоках даёт одинаковый хеш мира.

## Чего пока нет

Планировщика, который сам запускает независимые системы одновременно (например, «движение» и «анимацию»). Пока системы идут по очереди, и каждая распараллеливает свой обход. Решение и причины — в [docs/adr/ecs.md](../adr/ecs.md), пункт 5.
