# Бюджеты кадра, памяти и draw calls

- **Статус:** Принято. Цифры стартовые, уточняются по замерам профайлера (Q2) начиная с этапа 3
- **Дата:** 2026-10-14
- **Владелец:** Хранитель производительности (G2), распределение между подсистемами — оркестратор
- **Затрагивает:** все крейты с кодом, который работает каждый кадр или каждый ход

## Коротко

У каждой подсистемы есть «кошелёк»: сколько миллисекунд кадра, мегабайт памяти и вызовов отрисовки (draw calls) она может потратить. Сумма кошельков даёт 60 кадров в секунду на эталонном компьютере. Превышение бюджета блокирует слияние PR так же, как упавший тест. Если подсистеме не хватает, она не берёт чужое молча, а просит оркестратора перераспределить.

## Контекст

Критерий успеха (2): стабильный FPS при 10 000+ юнитов на экране и 50+ активных фракциях. Без бюджетов каждая подсистема оптимизирует «как получится», и о проблеме узнают на этапе интеграции, когда исправлять уже дорого.

## Решение

### Эталонная машина

Все цифры ниже относятся к одной конфигурации. Если замер сделан на другой машине, его пересчитывают через эталонную сцену.

| Компонент | Эталон |
|---|---|
| Процессор | 4 ядра / 8 потоков, уровень Intel Core i5-8400 или Ryzen 5 2600 |
| Видеокарта | уровень GTX 1060 6 ГБ / RX 580 8 ГБ, Vulkan 1.2 |
| Память | 16 ГБ ОЗУ |
| Диск | SATA SSD |
| Разрешение | 1920×1080, настройки «высокие» |

Цель: **60 FPS, то есть 16,6 мс на кадр**, без провалов ниже 45 FPS (22 мс) в эталонных сценах.

### Бюджет кадра в битве (10 000 юнитов на экране)

| Подсистема | Крейт | Бюджет, мс | Поток |
|---|---|---|---|
| Симуляция юнитов (движение, soft collision, бой) | `rm_battle` | 3,0 | рабочие потоки |
| Тактический ИИ | `rm_battle_ai` | 1,5 | рабочие потоки |
| Анимация (запечённая, считается на GPU) | `rm_crowd` | 1,5 | GPU |
| Рендер юнитов (instancing, LOD) | `rm_crowd` | 4,0 | рендер-поток + GPU |
| Рендер ландшафта и окружения | `rm_render` | 3,0 | рендер-поток + GPU |
| UI | `rm_ui` | 1,0 | главный поток |
| Резерв (звук, ввод, всплески) | — | 2,6 | — |
| **Итого** | | **16,6** | |

Симуляция битвы работает с фиксированным шагом (см. [determinism.md](determinism.md)). Бюджет 3,0 мс — это средняя цена шага симуляции в пересчёте на один кадр отображения.

### Бюджет кадра на карте кампании

| Подсистема | Крейт | Бюджет, мс |
|---|---|---|
| Рендер ландшафта, lightmap, splatting, границы | `rm_campaign_map` | 4,0 |
| Стриминг тайлов и виртуальная текстура | `rm_streaming` | 2,0 |
| Модели армий, городов, агентов | `rm_campaign_map` | 2,0 |
| Туман войны | `rm_campaign_map` | 0,5 |
| UI кампании | `rm_ui` | 1,5 |
| Резерв | — | 6,6 |
| **Итого** | | **16,6** |

Резерв на карте больше, потому что здесь работает анимация камеры и стриминг тайлов, где всплески неизбежны.

### Бюджет хода ИИ кампании (50+ фракций)

| Показатель | Бюджет |
|---|---|
| Полный ход всех ИИ-фракций (50 фракций, середина кампании) | ≤ 3 с |
| Одна фракция в среднем | ≤ 40 мс |
| Одна фракция в худшем случае | ≤ 150 мс |
| Дипломатия: оценка пар фракций | только внутри кластера и с соседями, не O(N²) |
| Обработка конца хода (экономика, постройки, рост) | ≤ 500 мс |

Ходы ИИ обрабатываются параллельно по фракциям (`rm_campaign_ai` на job system из `rm_core`).

### Бюджет мегаполиса (худший случай: центр города, 6 000 юнитов на улицах)

Тот же кадр 16,6 мс, что и в битве, но рендер ландшафта и окружения (3,0 мс) делится так: застройка 2,0 мс, occlusion culling 0,5 мс, стены и ворота 0,5 мс. Число юнитов в городе ниже, чем в поле, потому что дома и стены стоят дороже.

### Draw calls

| Сцена / подсистема | Лимит |
|---|---|
| Битва, всего за кадр | ≤ 2 000 |
| Юниты: один вызов на (тип модели × уровень LOD) | ≤ 400 |
| Перекраска всех регионов на карте кампании | **ровно 1** |
| Границы фракций (stencil) | ≤ 2 |
| UI, всего | ≤ 50 |
| Мегаполис, всего за кадр | ≤ 3 000 |

### Память

| Категория | Битва | Кампания |
|---|---|---|
| ОЗУ всего процесса | ≤ 4 ГБ | ≤ 4 ГБ |
| Видеопамять всего | ≤ 3 ГБ | ≤ 3 ГБ |
| Атласы текстур юнитов | ≤ 768 МБ VRAM | — |
| Кэш тайлов виртуальной текстуры | — | ≤ 1 ГБ VRAM |
| Состояние одного юнита в симуляции (горячие компоненты) | ≤ 128 байт | — |
| Состояние кампании (все фракции, регионы, персонажи) | — | ≤ 512 МБ ОЗУ |

### Загрузка

| Что | Бюджет |
|---|---|
| Запуск до главного меню | ≤ 10 с |
| Загрузка битвы | ≤ 15 с |
| Загрузка кампании | ≤ 20 с |
| Разбор всех текстовых файлов `data/` | ≤ 2 с |

### Правила для кода в горячих циклах

- Никаких выделений памяти в куче (`Vec::push` с ростом, `Box::new`, `String`) внутри шага симуляции и записи команд рендера. Используются кадровые аллокаторы и пулы из `rm_core`.
- Данные, по которым бегут каждый кадр, хранятся в формате SoA (структура массивов), см. [ecs.md](ecs.md).
- Никаких блокировок мьютексов на горячем пути; синхронизация — через граф задач job system.

## Порог регрессии

PR блокируется, если в любой эталонной сцене:

- время кадра выросло больше чем на **0,5 мс**, или
- память выросла больше чем на **5 %**, или
- число draw calls вышло за лимит из таблицы, или
- подсистема вышла за свой бюджет.

Снять блок можно двумя способами: оптимизировать или получить у оркестратора новое распределение бюджета, оформленное правкой этого файла.

## Почему не иначе

- **«Оптимизируем в конце».** Для 10 000 юнитов архитектура данных решает всё, и её нельзя поменять в конце проекта.
- **Один общий бюджет без деления на подсистемы.** Тогда непонятно, кто виноват в регрессии, и каждый агент считает, что тормозит сосед.

## Последствия

- С этапа 3 профайлер (Q2) обязан мерить мс по подсистемам на каждой сборке. До этого бюджеты проверяются микробенчмарками.
- Каждая подсистема размечает свою работу зонами `tracing` с именем крейта, чтобы замер был по подсистемам.
- Цифры будут меняться: это нормально, но только через правку этого файла.

## Как проверяем

Эталонные сцены (их строит Q2 в `benches/`):

1. Поле: 10 000 юнитов, две армии, общий бой.
2. Мегаполис: штурм центра города, 6 000 юнитов.
3. Кампания: ход ИИ при 50 фракциях, середина игры (ход 100).
4. Карта: быстрая прокрутка гипердетализированной карты от края до края.

Каждая сцена детерминирована (фиксированный seed, записанные команды), поэтому замеры сравнимы между сборками.
