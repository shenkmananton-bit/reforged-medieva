# ECS: собственная реализация на архетипах

- **Статус:** Принято
- **Дата:** 2026-10-14
- **Владелец:** агент ядра (C1)
- **Затрагивает:** `rm_core` и все крейты, которые хранят игровые объекты в ECS (`rm_battle`, `rm_campaign`, `rm_city`, ИИ)

## Коротко

Игровые объекты (солдаты, отряды, армии, поселения) хранятся в нашем собственном ECS из `crates/rm_core`. Он устроен на **архетипах**: сущности с одинаковым набором компонентов лежат в одной таблице, а каждый тип компонента — в отдельном плотном массиве (Structure of Arrays). Внешние ECS-библиотеки (`bevy_ecs`, `hecs`, `specs`, `legion`) не используем. У ядра вообще нет внешних зависимостей.

## Контекст

- Цель проекта — 10 000+ юнитов на экране и 50+ фракций с ходами ИИ на Data-Oriented Design (см. тему проекта и [budgets.md](budgets.md)).
- Реплеи требуют побитового детерминизма ([determinism.md](determinism.md)): порядок обхода сущностей, выдача id и параллельный обход не должны зависеть от запуска, хешера или числа потоков.
- Ядро — слой 0 ([crate-map.md](crate-map.md)); от него зависят все. Его API должен быть маленьким и предсказуемым, а раскладка памяти — под нашим контролем.

## Решение

1. **Архетипы + SoA.** Архетип = набор типов компонентов. Внутри него для каждого типа своя колонка (стёртый по типу `Vec`), плюс массив `Entity` по строкам. Обход запроса `(&mut Pos, &Vel)` — это линейный проход по двум массивам: процессор читает память подряд и векторизует цикл.
2. **Entity = индекс + поколение.** Освобождённые слоты переиспользуются по стеку (LIFO), поколение растёт при удалении. Выдача id детерминирована: одна и та же последовательность команд даёт те же id.
3. **Компонент — любой `'static + Send + Sync` тип**, без макросов и регистрации. Тип регистрируется при первом использовании.
4. **Запросы описываются типом**: `&T`, `&mut T`, `Option<&T>`, `Option<&mut T>`, `Entity` и кортежи до 8 элементов. Конфликт `(&mut T, &T)` ловится паникой при создании запроса. Изменяемые запросы требуют `&mut World`, поэтому заимствования проверяет компилятор.
5. **Параллельность внутри систем, не между ними (на этапе 1).** `World::par_for_each_mut` режет строки архетипов на непересекающиеся куски и раздаёт пулу потоков из `rm_core::jobs`. Системы пока выполняются по очереди; каждая сама распараллеливает свой обход. Это проще и уже загружает все ядра на «тяжёлых» системах (бой, мораль, движение).
6. **Порядок обхода детерминирован:** архетипы в порядке создания, строки по порядку. `HashMap` внутри мира используется только для поиска по ключу и никогда не обходится.
7. **Хеш состояния по компонентам:** `World::hash_component::<T>()` (FNV-1a, little-endian) — для контрольных точек `rm_replay`.

## Почему не иначе

- **`bevy_ecs`.** Мощный, но тянет свой планировщик, `Res`/`Query`-систему и десятки зависимостей; детерминизм порядка обхода и выдачи id не гарантирован контрактом. Мы бы подстраивали архитектуру M2 под Bevy, а не наоборот.
- **`hecs`.** Близок к нашему решению и мал, но параллельный обход и стабильность порядка — не его цель; любые правки пришлось бы держать форком. Своя реализация — около 1500 строк вместе с тестами, и мы понимаем каждую.
- **Sparse set (как в EnTT/`specs`).** Быстрое добавление и снятие компонентов, но обход нескольких компонентов идёт с прыжками по памяти. У нас главная операция — обход десятков тысяч юнитов каждый шаг, а смена набора компонентов редкая. Архетипы выигрывают.
- **Классические объекты (`Vec<Box<Soldier>>`).** В бенчмарке ядра обход 100 000 таких объектов примерно в 20 раз медленнее обхода ECS (см. [docs/core/benchmarks.md](../core/benchmarks.md)).
- **Планировщик систем с анализом доступа (как в Bevy) уже сейчас.** Отложено: пока систем мало, выгода маленькая, а сложность и риск для детерминизма большие. Вернёмся на этапе 3, когда появятся `rm_battle` и `rm_battle_ai`.

## Согласование с [determinism.md](determinism.md)

Расхождений нет. Что ядро даёт по пунктам того ADR:

| Требование | Где в `rm_core` |
|---|---|
| Фиксированный шаг 20 Гц | `sim::FixedTimestep::battle()` (`BATTLE_HZ = 20`), время в целых наносекундах |
| Счётный ГСЧ от `(seed, поток, шаг, сущность, вызов)` | `sim::random_u64`, `sim::Rng::for_entity`, потоки `sim::RngStream` |
| `dmath` вместо `sin`/`cos`/`atan2` из `std` | `rm_core::dmath` (только `+ - * /` и `round`, точность ~1e-7) |
| Детерминированные id сущностей | `ecs::Entity`, свободные слоты по стеку |
| Хеширование состояния по компонентам | `World::hash_component::<T>()`, `sim::StableHasher` |
| Независимость от числа потоков | тест `same_commands_same_hash`: 1, 4 и 8 потоков дают один хеш |

Одно уточнение: `hash_component` требует от компонента `Hash`. У `f32` его нет, поэтому компоненты с float-полями реализуют `Hash` вручную через `to_bits()`. Это осознанно: так автор компонента сам решает, что входит в контрольную сумму.

## Последствия

- Доменные крейты описывают данные как компоненты-структуры и пишут системы как функции над `&mut World`.
- Частое добавление и снятие компонентов дорого (переезд строки в другой архетип, ~0.2 мкс). Быстро меняющиеся флаги (бежит, в строю, в бою) лучше хранить полем внутри компонента, а не тегом.
- В ядре есть `unsafe`-код (колонки без типа, пул потоков). Каждая такая функция документирована условием безопасности, а случайные операции сверяются с простой моделью в тесте `random_operations_match_model`.

## Как проверяем

- `cargo test -p rm_core`: модельный тест мира, проверка вызова `Drop` ровно один раз, отказ «висячих» `Entity`, совпадение параллельного и последовательного обхода, одинаковый хеш на 1/4/8 потоках, эталонные значения ГСЧ.
- `cargo bench -p rm_core`: обход 10 000 и 100 000 сущностей; результаты записаны в [docs/core/benchmarks.md](../core/benchmarks.md).
